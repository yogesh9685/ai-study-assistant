5. FEATURE 1: ONBOARDING — END-TO-END FLOW

The Business Problem

A pandit can't accept bookings until they complete a 4-step onboarding and get admin approval. Each step collects different data. Admin must review a frozen snapshot — not live data — so a pandit can't game the review by editing after submission.

The 4 Steps

Step 1 → ProviderPersonalDetails  (pandit type, gotra, experience, profile photo)
Step 2 → ProviderAccountDetails  (bank/UPI info for payouts)
Step 3 → ProviderServiceConfig   (service capabilities, advance booking settings)
Step 4 → ProviderVerification    (Aadhaar/PAN upload, selfie, terms acceptance)

The Models

ProviderProfileProgress   ─── tracks current_step, completed_steps,
                              verification_status (DRAFT → SUBMITTED → APPROVED)
ProviderPersonalDetails   ─── Step 1 data (OneToOne with ServiceProvider)
ProviderAccountDetails    ─── Step 2 data
ProviderServiceConfig     ─── Step 3 data
ProviderVerification      ─── Step 4 data + GCS paths for documents
OnboardingSubmission      ─── snapshot (JSON) frozen at submit time
OnboardingAuditLog        ─── every action logged with ip, user_agent, changed fields

The Flow

1. GET /api/provider/onboarding/status/
   → Returns current_step, completed_steps, verification_status

2. GET /api/provider/onboarding/step/1/
   → Returns prefilled data if already saved

3. PATCH /api/provider/onboarding/step/1/
   → Validates, saves ProviderPersonalDetails
   → Updates ProviderProfileProgress.completed_steps = [1]
   → Writes OnboardingAuditLog entry

4. Repeat for steps 2, 3, 4

5. POST /api/provider/onboarding/submit/
   → Validates all 4 steps are complete
   → Creates OnboardingSubmission (JSON snapshot of all steps)
   → Sets verification_status = SUBMITTED
   → Sets submitted_at = now()

6. Admin reviews OnboardingSubmission snapshot (frozen, not live data)
   → APPROVED → provider.is_active = True → can accept bookings
   → REJECTED / PARTIALLY_REJECTED → notified with reason

Key Design Decision — The Snapshot

▎ "One tricky requirement was: admin should review what the pandit submitted, not what they may have edited afterward. My solution was OnboardingSubmission — when a pandit hits 'Submit', we serialize all 4 steps into a JSON field and store it as a snapshot. The admin review API serves this frozen snapshot. The pandit can keep editing live data (for a future re-submission), but it doesn't affect what's under review."

6. FEATURE 2: SLOT LOCK — END-TO-END FLOW

The Business Problem

When a user selects a time slot and starts payment, that slot must be held for them so no other user can book the same pandit at the same time. But we can't create a confirmed booking before payment succeeds. Solution: a temporary lock, like a shopping cart hold.

The Models

SlotLock
  ├── service_provider (FK → ServiceProvider)
  ├── service_seeker (FK → ServiceSeeker)
  ├── pooja (FK → PanditPooja)
  ├── booking_date, start_datetime, end_datetime
  ├── venue_lat, venue_lng, venue_address
  ├── expires_at          ← TTL for the lock (configurable, default 10 min)
  ├── samagri_selection, contact_no, special_instructions
  └── UUID primary key

Constraint: UniqueConstraint(service_provider, start_datetime)
  → Only one active lock per slot per pandit

Full Flow

1. User sees available slots (GET /api/bookings/slots/)
   → SlotGenerator iterates time slots for the day
   → Each slot checked against existing bookings + active locks
   → Cached in Redis per pandit (invalidated on any lock/booking)

2. User selects slot → POST /api/bookings/lock-slot/
   → LockSlotView validates input via LockSlotInputSerializer
   → Calls LockSlotUseCase.execute()

3. LockSlotUseCase runs validations (in order):
   a. Pooja is active and valid
   b. Slot time aligns to interval (e.g., must be :00 or :30)
   c. Coordinates valid and within service area
   d. Not in the past
   e. Duration matches pooja.duration_minutes
   f. Within working hours (e.g., 6am–9pm)
   g. Same calendar day (no midnight crossings)
   h. Lock limits not exceeded (anti-hoarding)

4. _lock_slot_atomic() → DB transaction with SELECT FOR UPDATE:
   a. SELECT FOR UPDATE on ServiceProvider row (acquires row-level mutex)
   b. SELECT FOR UPDATE on all active locks + confirmed bookings for pandit
   c. SlotValidator checks if new slot overlaps with any blocked slot
      → Also checks travel time between back-to-back bookings
   d. Delete any expired locks for same slot (stale cleanup)
   e. SlotLock.objects.create(..., expires_at=now()+10min)
   f. On IntegrityError → "Slot just taken by another user"

5. SlotLockAudit.log_lock_created() → audit trail

6. Redis cache invalidated for this pandit

7. Response to user:
   { lock_id, expires_at, start_datetime, end_datetime, reserved_until }

8. User completes payment → POST /api/bookings/confirm/
   → Verifies lock exists and not expired
   → Verifies payment with Razorpay
   → Creates Booking from lock data
   → Deletes SlotLock
   → SlotLockAudit.log_lock_confirmed()

9. If user abandons → Celery periodic task expires lock → SlotLockAudit.log_lock_expired()

14. N+1 QUERY PROBLEM AND OPTIMIZATION

The Problem We Had

# BAD: N+1 — 1 query for bookings + N queries for each provider name

15. THE MOST CHALLENGING TASK — SLOT LOCK RACE CONDITION

The Problem

▎ "Two users can try to book the same pandit at the same exact time. If both requests arrive simultaneously at 10:30am, both might read 'slot available' and both try to create a SlotLock. Without protection, both succeed → pandit gets double-booked."

My Solution — SELECT FOR UPDATE (Pessimistic Locking)

@transaction.atomic
def _lock_slot_atomic(self) -> SlotLock:
    # Step 1: Acquire pandit-level mutex
    # This blocks ALL other concurrent requests for this pandit
    ServiceProvider.objects.select_for_update().get(id=self.pandit.id)

    # Step 2: Read all existing locks + bookings with row-level locks
    # No other transaction can modify these rows while we hold them
    locks = SlotLock.objects.select_for_update(nowait=False).filter(
        service_provider=self.pandit,
        expires_at__gt=now
    )
    bookings = Booking.objects.select_for_update(nowait=False).filter(
        service_provider=self.pandit,
        status__in=['confirmed', 'pending', 'started']
    )

    # Step 3: Validate no conflict (SlotValidator checks overlap + travel time)
    self._validate_slot_available(locks + bookings)

    # Step 4: Create lock — UniqueConstraint is last line of defense
    try:
        return SlotLock.objects.create(...)
    except IntegrityError:
        raise SlotLockError("LOCKED", "Slot just taken by another user")

Why two layers of protection?
- SELECT FOR UPDATE → prevents concurrent reads from seeing stale state
- UniqueConstraint(service_provider, start_datetime) → DB-level guarantee even if code has a bug

Idempotency Key

▎ "We also added idempotency keys to the lock-slot endpoint. If a user double-taps 'Book Now', both requests arrive. The idempotency middleware checks Redis for a key — if the same key already processed, it returns the cached response instead of creating a duplicate lock."

16. ONE DIFFICULT BUG — UNIQUE CONSTRAINT ON EXPIRED LOCKS

The Bug

▎ "We had a UniqueConstraint(service_provider, start_datetime) on the SlotLock table to prevent double-booking. The constraint worked great. But users reported they couldn't re-lock a slot after their first lock expired. The slot showed as available in the UI, but the lock API returned 'Slot just locked by another user.' This was a confusing failure."

Root Cause

▎ "The lock expired (TTL passed) but the SlotLock row was NOT deleted — Celery cleanup ran every few minutes, not instantly. So when the user tried to lock the same slot again, Django tried to INSERT a new SlotLock with the same (service_provider, start_datetime) — but the old expired row still existed in the DB. The unique constraint fired an IntegrityError, which we caught and returned as 'slot taken' — completely wrong error."

The Fix

@transaction.atomic
def _lock_slot_atomic(self) -> SlotLock:
    self._acquire_pandit_mutex()
    blocking_slots = self._fetch_blocking_slots_with_lock()
    self._validate_slot_available(blocking_slots)

    # Proactively delete any EXPIRED lock for this specific slot
    # before trying to INSERT — prevents IntegrityError on expired rows
    SlotLock.objects.filter(
        service_provider=self.pandit,
        start_datetime=self.start_datetime,
        expires_at__lt=timezone.now()   # ← only expired ones
    ).delete()

    return self._create_lock_safe()

▎ "The key insight was: the fetch of blocking slots only fetches locks with expires_at > now (active locks), so expired locks don't show as conflicts. But the unique constraint doesn't know about expiry — it applies to ALL rows. By deleting expired rows for the specific slot before inserting, we eliminated the IntegrityError while keeping the constraint as a true last-line defense."

17. PERFORMANCE OPTIMIZATION — SLOT AVAILABILITY CACHE

Problem

▎ "The 'get available slots' API was heavy — it had to fetch all active locks and bookings for a pandit on a given day, then iterate through every 30-min slot and check each one for conflicts. With multiple users hitting this simultaneously while browsing, the DB was getting hammered."

Solution — Versioned Redis Cache

slots_cache = VersionedCache("booking_slots", ttl=120)  # 2-minute TTL

class GetAvailableSlotsUseCase:
    def execute(self):
        cache_key = f"{self.pandit.id}:{self.booking_date}:{self.pooja.id}"
        cached = slots_cache.get(cache_key)
        if cached:
            return cached

        result = self._compute_slots()  # DB-heavy computation
        slots_cache.set(cache_key, result)
        return result

Cache invalidation:
# In LockSlotUseCase, after creating a lock:
def _invalidate_pandit_cache(self):
    slots_cache.invalidate(self.pandit.id)
    calendar_cache.invalidate(self.pandit.id)

▎ "The cache is invalidated immediately whenever a lock is created or a booking is confirmed/cancelled. This means users always see accurate availability, and the DB is only hit once per 2-minute window instead of on every request."

20. WHAT IS A QUERYSET

▎ "A QuerySet is a lazy collection of DB rows. It's lazy — no SQL is executed until you evaluate it (iterate, call .first(), .count(), etc.). This lets you chain filters:
▎ Booking.objects.filter(service_provider=pandit).filter(status='confirmed').order_by('-created_at')[:10]
▎ # Only ONE query executes, with all filters combined
▎ get() raises DoesNotExist if zero results, or MultipleObjectsReturned if more than one. filter() always returns a QuerySet, even if empty. I used get() when I expected exactly one row (like SlotLock.objects.get(id=lock_id)), and filter().first() when I wasn't sure."

        {"error": e.code, "message": e.message},
        status=status.HTTP_409_CONFLICT
    )

Standard error response shape:
{ "error": "SLOT_LOCKED", "message": "This slot is already booked." }
DRF's serializer.is_valid(raise_exception=True) auto-returns 400 with field errors.

Provider profile photo, Aadhaar/PAN scan, selfie:

1. Frontend requests a signed GCS upload URL from Django
   POST /api/provider/onboarding/upload-url/
   → Django generates a signed PUT URL (time-limited) for GCS

2. Frontend uploads file directly to GCS using the signed URL
   (no file passes through Django server — saves bandwidth)

3. Frontend sends the GCS object path to Django
   PATCH /api/provider/onboarding/step/1/ { "image_path": "providers/123/photo.jpg" }

4. Django stores only the GCS object path (string) in the model
   On read, generates a signed GET URL for the frontend to display

28. WHAT I'D IMPROVE WITH MORE TIME

▎ "Three things: First, replace the polling-based slot expiry cleanup (Celery periodic task) with a Redis KEYSPACE notification — when the lock key expires in Redis, a webhook fires to delete the DB row and log the audit. Second, add database-level row-level security for multi-tenancy instead of filtering by provider in every query. Third, the slot availability cache uses a simple TTL — I'd make it event-driven using Redis pub/sub so when a lock is created by any server instance, all instances invalidate immediately, which matters as we scale horizontally."
